## Phase 3: Loader with little manual work per patch

Comes before the admin phase: the loader decides which named values exist per ability (the editor offers them for selection), and a fresh load into the new format is cheaper than migrating the old documents, which hold no valuable manual data yet.

The loader only collects data (numbers, named values, texts, cast times) and builds no structure. Structure comes from manual entry (Phase 4) or AI drafts (pilot in Phase 4, scaled in Phase 6).

### Data model and formulas

- [x] **Decided: raw data is stored.** The whole CDragon file per object and patch goes into its own collection, separate from the finished objects and never read by the user API (measured for Veigar: 133 KB with tooltips and wiki templates, so ≈ 23 MB per patch for champions). It is the lookup for manual entry and the source when later features need more fields (dash times, animations), without reloading old patches. Not relying on CDragon keeping old folders forever
- [x] **Decide:** the loader stores everything it scrapes in its own raw models, so nothing gets lost. The finished objects (`Champion`, `Ability`, …) are built from the raw data and keep only what the simulation needs. Open: are the numbers copied into the finished objects (a build step reruns every patch) or referenced by name and resolved at simulation time? Either way the hand-made structure must survive a new patch
  - **Decided: reference by name.** Each document has a loader-owned `values` field (`BaseDamage = [80, 120, …]`, overwritten every patch) next to the hand-made rules, which use the name (`BaseDamage + APRatio * ap`) and are never touched by a patch. The simulation resolves the name by rank like `by_rank(...)`. No build step, and "manual effect data lives per patch" (backlog) shrinks because the structure changes less often. Risk: Riot renames a value; the loader sees that a name used by a rule is gone and marks the ability unvalidated
  - **Formula syntax:** rules use Riot's names as they are (no own names, they are the link between patches). A bare name is the rule's own ability; other abilities with a prefix (`q.TumbleCDReduction`). No `by_rank`/`by_level` in hand-written formulas: a `DataValues` name resolves by rank (all lists have 7 entries = rank 0–6; constants are equal everywhere), and level scaling only appears in `mSpellCalculations`, which the loader translates into our syntax once (Darius: `BleedDamagePerStack = "by_level(13, …, 30) + 0.3 * bonus_ad"`). Calculations are named values too, so a rule is often just `amount: "TotalDamage"`; a formula in `amount` is still allowed where Riot's tooltip calculation doesn't cover the mechanic (Veigar R's missing-HP scaling). The translator knows the ~11 part types and reports unknown ones instead of guessing. A patch that changes a calculation's structure (not just numbers) is taken over but marks the ability unvalidated
  - ✅ **Renamed `scaling` → `amount`** in `Damage`, `Attack`, `Heal`, `Shield` and `PetAttack` (same name as `ModifyCooldown`/`PayCost`). The old admin editor components still say `scaling`; they are replaced by the Phase 4 rule editor
  - **Everything the loader delivers goes into `values`; every formula field is hand-owned**, also `cost` and `cooldown`. The loader adds the spell fields under Riot's field names (`cooldownTime`, `mana`; they can't clash with the mostly capitalized `DataValues`, Gunblade has its own `Cooldown`), and `cooldown`/`cost` default to those names. A formula like Veigar W's (`cooldownTime` is 0 there, the script uses `BaseCooldown`) survives every patch
  - Not now: a hand-owned `formulas` field for own named formulas (separate from the loader's `values`, which every patch overwrites). Purely additive, can come later if `amount` formulas get messy
  - To clarify when building the patch flow: does CDragon show mechanic changes? Likely signals: value names added/removed, changed `mSpellCalculations`, changed tooltip text. Behavior that lives only in game scripts is not exported, so the wiki patch notes probably stay a second net (objects named there get flagged)

### Description texts

  - **Decided:** the CDragon tooltip (`lol.stringtable.json`, e.g. `spell_veigarbalefulstrike_tooltip`) is loader-owned and required; a changed tooltip is a validation signal. Its placeholders are our names (`@TotalDamage@`), Riot's cross-references match our prefix idea (`@Spell.VeigarPassive:dQKillStacks@`)
  - The wiki text with its notes is required for the first load: what the game logic decides (spell shield interaction, which abilities can be cast during others like Riven E → R, on-hit, can't crit) is not in CDragon. Stored as text, not parsed into fields. On patches, the full text is refetched when the wiki page has a newer revision (wiki API revision id), so a late wiki edit is picked up on a later run; patch note lines stay in `changes`. A missing or outdated wiki text blocks nothing
  - CDragon's hints (tooltip tags like `<magicDamage>`, spell tags like `Trait_AttackReset`/`Trait_Shield`, flags like `mCantCancelWhileWindingUp`) are shown in the editor as suggestions. Crit hints: Vayne Q has an explicit `CanBonusDamageCrit = 0`; Darius W's `ADRatio` is the whole attack (1.4–1.6 × AD) while Vayne Q's `TotalADRatio` is only the bonus, which may tell whether the bonus can crit (check against the wiki)

### Automatic patching

- [x] Read each champion's adaptive type (physical/magic) into `Champion.adaptive_type`: from CDragon (`mAdaptiveForceToAbilityPowerWeight`), cross-checked against `Module:ChampionData/data` (`adaptivetype`)
- [ ] **Automatic patching:** load the new CDragon data, overwrite `values`, copy the hand-made part forward unchanged, and decide per ability whether it stays validated:

  | Change | Result |
  |---|---|
  | Only numbers | stays validated |
  | Structure of a calculation that a rule uses by name, fully understood by the translator | stays validated (the rule follows automatically) |
  | Structure of a calculation that no rule uses by name while rules use its values (the rule rebuilt it by hand), or a part the translator doesn't know | unvalidated |
  | A name a rule uses is gone | unvalidated |
  | A new name appeared | unvalidated (probably a new mechanic) |
  | Tooltip text changed, numbers equal | unvalidated |
  | Named in the wiki patch notes, but nothing changed in CDragon | unvalidated, marked "patch notes only" (mechanics CDragon can't show) |

  `changes` holds only the changes of **this** patch (loader diff and patch note lines). A copied document starts with empty `changes`, so the history of an ability is the `changes` of each patch. Unvalidated abilities are the input for AI drafts later (Phase 4/6)
  - ✅ For champions. `changes` is `list[Change]` with `source` (`data` = loader diff, `patch_notes` = wiki line); "patch notes only" is an unvalidated container without `data` lines. Old documents with plain strings parse as patch note lines. Stat changes are only lines; `Champion.validated` is computed: all abilities and the passive validated. Items, runes and summoner spells still extend the old list (old loader)
  - **Decided: hotfixes overwrite the patch** instead of copying every document (CDragon also rewrites its folder in place). A hotfix reruns the loader part on the same documents and diffs against the stored raw data; its lines are added to the patch's `changes`. Check once a day: `content-metadata.json`'s build number unchanged ⇒ nothing; new build ⇒ reload and diff, a bugfix-only build gives an empty diff and changes nothing. The wiki hotfix list stays a second net.
  - **Decided: `hotfix` is no longer part of a document's identity.** With overwriting, a key `(name, patch, hotfix)` would change on every hotfix for all documents, and every client would need two values to find the current data. Identity is `patch` (+ name/id); the patch keeps `build` (CDragon's `content-metadata.json`) and `updated_at` (last hotfix run). Which `changes` line came from a hotfix was first left unmarked (the patch's `updated_at` tells that and when it was hotfixed), then marked per line, see below. Old documents keep a stray `hotfix: null`, which the models ignore; the unique indexes are rebuilt at startup (`database._unique_index`), a database with old hotfix copies logs an error instead (the main DB gets reloaded after Phase 4 anyway)
  - ✅ Hotfix run (`patchloader.load_hotfix`): `check_updates` gives the new patches and `pending_hotfix` for the latest complete patch: a new build, or wiki hotfixes from a later day than `updated_at` (or the load's `timestamp`). Wiki hotfixes only carry a day, so one added later on the day of a run is missed; the build still catches its numbers. The hotfix runs before newer patches, so they start from the corrected data. Champions: reloaded and diffed against their **own** stored raw data (all of them on a new build, only the named ones on a wiki-only hotfix), `keep_earlier_changes` appends the new lines without duplicates, `changed_champion_count` only counts champions that had no changes yet. Items, runes, summoner spells (`patchloader2.hotfix_others`): named ⇒ lines appended, `validated = False`, in place; new or removed objects in a hotfix are only logged. A patch load takes the hotfixes already on the wiki with it (`notes_with_hotfixes`), because CDragon already has their numbers; otherwise the next check would read them as "patch notes only" and unvalidate. Several hotfixes naming the same object keep the lines of each (`hotfix_notes`)
  - ✅ Hotfix lines marked: `Change.hotfix: datetime | None = None` (`None` = came with the patch, else the date of the hotfix run that found it; the default keeps old documents loading), so after a hotfix the editor can show which lines are new since the patch was entered. One timestamp per run (`load_hotfix`), also stored as `Patch.updated_at`, so a line's date matches the run. `change.with_hotfix_lines` is shared by `keep_earlier_changes` (champions) and `hotfix_others` (items, runes, summoner spells): lines are compared without `hotfix` (`Change.same_line`), otherwise a patch line found again by the hotfix run would count as new; a line already there keeps its earlier date
  - ✅ Extra abilities (Nidalee's cougar Takedown/Pounce/Swipe) have no CDragon spell of their own: their numbers live in the spell of the slot they rank with (`rank_from`, Pounce's damage is R's `PounceDamage`). So a patch note on an extra ability counts as backed by data when that slot has data lines (`_data_lines_behind`). Trade-off: any data line on R backs it, even an unrelated one; matching the note's numbers to a line was too fragile for the one champion that has extras today
  - ✅ Charges: the loader reads `mAmmoRechargeTime` and `mMaxAmmo` as `ammoRechargeTime`/`maxAmmo` (rank 1 at index 1 like `Cooldown`), only when `mMaxAmmo` is at least 2 on some rank: 52 spells carry a recharge time, but many with no or a single ammo (Rengar 1, Irelia R -1, Rakan, Kayn, Taric none). 16.21 gives 21 abilities (Zyra W, Caitlyn W, Teemo R, Ashe E, Corki R, …). New hand-owned formula field `Ability.charges` ("0" = none) next to `recharge`; a first load sets `charges = "maxAmmo"`, `recharge = "ammoRechargeTime"`, and `cooldown` stays the time between casts. Not real charges despite the data, to fix by hand: Warwick W (2 ammo, 3 s), LeBlanc R (the mimic), Karthus Q (1 s). The simulation doesn't use `charges`/`recharge` yet. Existing documents get the two values on their next patch, which unvalidates those abilities once ("new values"), as it should: their rules don't know charges yet
  - ✅ Real run on 16.21.1 (throwaway DB, no build stored yet ⇒ full reload): 173 champions in 40 s, indexes migrated, the only diff was Ashe's `crit_damage: 2 ⇒ 1` (a translator fix since the 16.21 run, not a hotfix). Removed with it: the old loader's entry points and champion path in `patchloader2` (only tests still called them)

  - Source: CommunityDragon for all images. Data Dragon only has the client's shop/overview icons and misses recasts and forms (Sion W recast); the spell data names each spell's icon path. Check that sizes are uniform
  - Every patch downloads all images and stores them under a hash of their pixels (see Pixel hash below) (`VeigarBalefulStrike.3fa2c1.png`).   - Images are never deleted, so items removed from the game keep their image in old patches

Each patch the loader points an extra ability's `image` to its key; a stage keeps only the key, the frontends look it up and fall back to the ability's image. A key the icons lack is a warning (Riot renamed the file), and the owner keeps its old image. Other folders hold borrowed placeholders (Sion's Q missile shows Ezreal's R, Jhin's quest icons), so they're left out, and so are skin variants (`_skin<number>`: Aphelios' passive in 7 skins; Wukong's `monkeykingstoneskin` is his passive and stays). Each URL downloads once per champion, a slot's icon included. Real run: Sion 8, Nidalee 10, Aphelios 24 without the skin variants (his five weapons have their own icons), no failures, all 64×64. The test group's Nidalee names `nidalee_q2`, `_w2`, `_e2`
  - ✅ Splash art (`Champion.splash`, group `splash`): the base skin's centered splash (1280×720 JPG, ~90 KB), a background for the champion's page later. The uncentered art (1215×717) was the other choice; centered fits a 16:9 background. `store_image` keeps the URL's extension. A failure keeps the old splash. Real run: Sion, Aphelios, Hwei, Wukong
  - ✅ Pixel hash (Pillow 13.0.0, the only new dependency): Cloudflare serves CDragon's files sometimes as the original, sometimes recompressed by its "Polish" (`cf-polished: ok, orig_size=1256`; Precision's tree icon 1256 ⇒ 702 bytes, Sion's splash 86231 ⇒ 83412), so one image got two file names. The hash now covers the decoded pixels as RGBA with fully transparent pixels zeroed: Polish turns RGB into RGBA and zeroes the color under invisible pixels (all 102 differing pixels of the tree icon had alpha 0). Checked on original/polished pairs of a tree icon, a spell icon, a champion icon and a splash; two real runs in a row write no duplicates. A download that isn't an image (an error page) is a `LoadError` 415 now. Old file names stay valid; each image gets its new name once, with the next load
  - ✅ Rune trees: the five icons come from the `PerkStyle` records of `perks.cdtb.bin.json` (`mIconTextureName`, already downloaded for the runes; the name from the string table), stored on `Patch.rune_trees` like the masterwork border, on a load, a patch and a hotfix with new sources. `/rune/trees/{patch}` (was without a patch) returns them; 32×32 like the old files.
